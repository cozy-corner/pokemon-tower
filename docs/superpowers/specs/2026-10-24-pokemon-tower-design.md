# ポケモンタワーバトル 設計書

## 目的と背景

「どうぶつタワーバトル」(動物を交互に積み、先に崩したほうが負けになる物理積み木ゲーム)のポケモン版を、**個人・家庭内で**遊ぶために作る。

- 主なプレイヤーは5歳の子供。縦長のブラウザゲームとして、タッチでもマウスでも遊べる。
- 子供は Pokémon GO や Duolingo のような**ひとりで進められるゲーム**に慣れている。似た積み木ゲームの経験はない。
- 参考にした先行作品: Facebook 上の「Pokémon Tower Battle」(2019年提供開始、現在は終了)。ルールは本家と同じ(角度と位置を決めて落とす、交互に積む、落とした側が負け)。モンスターボールで落とすポケモンを入れ替える仕組みがあった。
  出典: https://www.4gamer.net/games/124/G012479/20191225020/
- 素材は pokemondb.net/sprites のスプライト。権利は任天堂・ゲームフリークにあるため、**家庭内利用に限り、外部に公開・配布しない**。

## ゴール / ノンゴール / アンチゴール

**ゴール**
- 5歳がタップとドラッグだけで、ひとりで楽しく遊べる。
- 家の Wi-Fi 内で、別端末同士の対戦ができる(第2段階)。
- スプライトの見た目どおりの輪郭で積める(四角い判定にしない)。

**ノンゴール**
- インターネット公開、ランキング、アカウント、課金。
- ポケモン全種類の網羅(初期は一部でよい)。

**アンチゴール(技術的に動いても失敗とみなす)**
- 触っていないのにタワーが勝手に揺れて崩れる。子供が「自分のせいじゃない」と感じる。
- ボタンや文字が小さく、5歳が操作できない。

## 制約

- 実行環境は、縦向きのブラウザ。Mac でサーバーを立て、家の Wi-Fi の LAN アドレス(例 `http://192.168.x.x:8000`)で開く。遊ぶ端末の `localhost` はその端末自身を指すので使えない。
- サーバーは遊ぶたびに保護者が起動する。
- 画像は pokemondb 側の要望(ホットリンク禁止)に従い、ローカルに保存して配信する。ダウンロード用スクリプトを `scripts/` に置き、再実行できるようにする。
- **画像ファイルは git の commit 対象外**にする(ユーザー決定。権利の都合)。`.gitignore` に画像の置き場を書き、スクリプトだけ commit する。

## 確認済みの事実(スプライト調査)

試作用に5種類のスプライトセットを取得し、ピカチュウ、ゲンガー、イーブイ、ラプラス、カビゴン、リザードンの6匹で輪郭抽出を試した。

- どのセットも背景が透明で、アルファ値から輪郭を取れる。
- 試作では HOME(128×128px)の輪郭が最も滑らかだったが、素材としては誤った選択だった。最終的な素材は PokeAPI の dream-world SVG(ユーザー決定、下の「決めたこと」を参照)。
- X/Y のリザードンは翼が細長い弧になり、積みにくい形だった。
- Sword/Shield(120×112)と Black/White(96)はドット絵調で、拡大するとギザギザやぼやけが出る。
- 穴のあるポケモン(リザードン)がある。細い部位(尻尾、耳、翼)は輪郭の単純化で崩れやすい。

## 方針の選択(Approaches)

物理エンジンについて2案を検討し、**B を選択**した(ユーザー決定)。

| 案 | 内容 | トレードオフ |
|---|---|---|
| A | Matter.js | 導入が簡単。積み上げ時の微小な揺れが出やすい可能性がある(一般的な知識にもとづく見立てで、未検証)。 |
| **B(採用)** | **Planck.js**(Box2D の JavaScript 版) | 積み木系で実績があり、安定していると見込む。導入の手間はやや増える。 |

案 B の安定性は動かして確かめる。アンチゴールの「勝手に崩れる」が起きるなら見直す。

## 設計(決定済みの部分)

### 全体
- ブラウザで動く **TypeScript + Vite**(ユーザー決定)。物理は Planck.js。遊ぶときの配り方は、Vite の開発サーバーを家の Wi-Fi 内の他端末から開ける設定にするか、ビルドして固めたファイルを配るかを、第1段階の最後に、実際に遊べる状態で Mac と、遊ぶ端末で試して決める(どちらも未検証。遊ぶ用途では後者のほうが安定する可能性がある)。
- 素材は **PokeAPI の dream-world SVG**(`.../sprites/pokemon/other/dream-world/{図鑑番号}.svg`、ユーザー決定。HOME は以前の誤った選択)。SVG は256px の長辺に描いて輪郭を取り、大きさは実際の身長(`data/heights.json`、PokeAPI)を対数で圧縮して長辺に割り当て、SVG は縦横比だけに使う(`src/geometry/sprite-size.ts`)。

### 段階
1. **第1段階: 1台の端末で遊べるひとり用の積み上げ。**(ユーザー決定。対戦は含めない)
2. **第2段階: 対戦。** 家の Wi-Fi 内で別端末同士が対戦する。方式や細部は第1段階のあとに決める。
   - メモ(想定であり決定ではない): ルールは本家どおり「落とした側の負け」。物理の計算をどこでやるかなど、方式は第1段階のあとに決める。

### ルール(ユーザー決定)
- **ひとり用: 落ちても終わりにしない。** 積めた数と高さを記録する。
- **落とすポケモンはランダムに出る。入れ替え(モンスターボール)は入れない**(ユーザー決定)。元の作品にあった仕組みだが不要とした。積みにくい形が続いても、ひとり用は落ちても終わらないので詰まない。
- 画面は**縦向き**(ユーザー決定)。タワーが高くなったら画面を上に動かす(提案)。
- bun と Node のバージョンは `mise.toml` で固定し、マシンに入っているものに頼らない。第1段階のサーバーは、ゲームのファイルを遊ぶ端末に配る役で、Vite を使うため Node 上で動く。第2段階のサーバーの言語は、そのとき決める。
- 「勝手に崩れない」の判定基準: 何も触らずに30秒置いて動かないこと。満たせなければ、別の物理エンジンへの切り替えを検討する。(提案)

### 操作(提案)
- ドラッグで位置、ボタンで回転、DROP ボタンで落下(Pokémon Tower Battle の画面に合わせる。指を離しても落ちない)。
- キーボードでも遊べる。`h` `l` / `←` `→` で位置、`k` / `↑` / Space で回転、`j` / `↓` / Enter で落下(vim のキーバインドと矢印キー)。
- ボタンと当たり判定は大きめにする。5歳が読めなくても分かるよう、文字より絵やアイコンを使う。

### 当たり判定
- スプライトのアルファ値から外側の輪郭を取り、頂点数を抑えた多角形にして Planck.js に渡す。
- 穴は無視する(外側の輪郭だけを使う)。
- 離れた複数の島(例: 体と離れた炎)は、すべてを1つの剛体の当たり判定に入れる(ユーザー決定)。数画素のゴミだけ無視する。すき間を埋めて1つの島にはしない。
- 細い部位が崩れすぎない単純化の程度は、実際のスプライトで目視確認して決める。

## 提案としての仮置き(未確認。直してよい)

- **ポケモンの範囲(ユーザー決定)**: 全種類(1025匹)を対象にする。名前の一覧は pokemondb のスプライト一覧ページから自動で取る。dream-world の SVG があるのは936種類で、無い89種類は `data/exclusions.json` に入れて除外する(別の絵で補わない)。名前→図鑑番号は pokemondb の全国図鑑ページから `data/dex.json` に取る。
- **除外リスト(提案)**: 輪郭抽出のとき、細すぎる形や、複数の島に分かれる形を機械で見つけて印を付け、変なものは除外リストに入れて出さない。積みにくい形が子供に向くかは未検証。
- **進み具合の演出**: 積んだ数に応じてポケモンが増えるなど。第1段階の後に検討する。

## 実装者に任せる部分

- ディレクトリ構成、Vite の設定の細部。
- 輪郭の単純化アルゴリズムと許容誤差。
- 画面レイアウト、効果音、落下位置のガイド表示。
- 対戦での「落とした」の判定の細部(台座から落ちた、一定時間動き続けた、など)。
